## 1. Context, outcome and authority

The owner prefers the approved Budget concept's presentation and finds the production page too
text-heavy and overwhelming. This handover specifies a faithful adaptation of that concept to the
real Budget subsystem, beginning with Budget rather than a redesign of the whole application.
The request authorizes this plan; implementation is to be requested in the small bursts below.

The implementation drift is specific: `Budget.tsx` currently places `BudgetLifecycle` and
`BudgetAttention` before the overview. Lifecycle exposes account, frequency, rollover and operational
controls in the page. The main numbers and goal content compete with repeated explanations and
similar glass panels. The concept instead leads with everyday remaining and the income plan,
groups everyday costs and commitments, and reveals detailed tasks only when requested.

**Outcome:** a user opening an existing budget should first understand the selected dates, everyday
remaining, spent versus planned, expected versus received income, and signed unallocated capacity.
They should then find category detail, commitments, goals and checks in a clear hierarchy.
Important uncertainty remains adjacent to the affected figure; detailed instructions appear within
the task that needs them. Functional reachability must improve alongside visual fidelity.

BUI phases are presentation work inserted before completing M7.3/M7.4 human validation. They do
not renumber M0–M7 or close the existing R01–R05 findings. M7.2's 64-state/260-check evidence is a
historical baseline; changed flows need fresh accessibility verification. Release remains No-Go.

## 3. Implementation boundaries

- Keep the authenticated `/budget` route, existing application header/rail, `BudgetProvider`,
  source/plan/method versions, owner gates and Edge command boundary. Avoid an application-shell
  rewrite. The concept's second header/rail/footer must not be copied into the route.
- Keep integer cents and shared date helpers. Formatting uses `fmtCents`. Display adapters may
  map bounded server rows, but never rebuild ledger totals from `DataContext` transactions.
- Preserve exact Save/Undo/recovery semantics, per-period/current-and-future choices, account roles,
  explicit gaps, immutable reviewed history and source invalidation. Task close is not save cancellation.
- No database migration or server calculation change is expected for the presentation work. If a
  required display lacks a reliable field, record a bounded dependency instead of inventing a value.
- No app-wide token replacement, default theme change, personal migration or flag enablement.
  Use the dedicated disposable manual preview for owner review.
- Keep the concept runnable and independent as a reference. Production must not import runtime
  modules from `src/concept/`; move only clearly reusable presentational assets with attribution.

Use independent dimensions for known/unavailable value, planned/recorded basis,
coverage, freshness and provisional status, as resolved in BUI-01. A provisional
value may also be stale. A genuine manual planning amount may be known while observed
spending is unavailable; evaluate each field independently. Do not type-cast nulls into numbers.
Use plan amounts freely as plan amounts; qualify evidence-dependent balances appropriately.

| Display | Production source / rules |
| --- | --- |
| Everyday planned | Saved everyday item `planned_cents` / its selected-period allocation |
| Everyday spent | Everyday item `used_cents`, subject to source validity and coverage; never total net spending if some costs consume reserves/bills |
| Everyday left | Authoritative everyday item `remaining_cents`, including applicable carry and rights movements; do not substitute income minus all expenses or naive planned-minus-spent |
| Expected income | `snapshot.revision.income_cents`, labelled planned; one-off drawdown stays separate |
| Received income | `snapshot.actuals.earned_income_cents` only when applicable account scope/facts are available; no-bank means unavailable observed activity, not verified zero |
| Still to plan / funding gap | `snapshot.unallocated_cents`; preserve negative sign and distinct future-template gap |
| Category planned/spent/left | `details.limits` canonical amounts/usage/remainders, taxonomy stable IDs; Other uses the corresponding server fields |
| Goal purpose/state/target | `BudgetItem.config`, stable `line_id`, archive/pause state and existing `goalEstimate` helper |
| Goal reserve/progress | `reserve_cents`, `net_purchases_cents`, bank/user evidence as separate measures. Do not add bank/user confirmations to the reserve or assume they are disjoint. A combined confirmed-progress segment needs a proven unique-evidence mapping first. |
| Days remaining | Selected period and server lifecycle `as_of` with existing local-date helpers; exclude today only if the copy says “after today”; no millisecond/DST arithmetic |
| Historical comparison | Existing lifecycle `facts` and immutable `review.payload`; latest source corrections must not replace the original reviewed values |

The goal progress treatment should visually distinguish planned from confirmed, as the concept
does, but must not imply a new total until BUI-01/BUI-03 prove its semantics. Keep explicit text
amounts if a truthful composite track cannot yet be drawn. Decorative meters may clamp visual
fill to 0–100%; signed overage and true amounts remain textually visible.

UI state stays local: selected tab, expanded groups and the currently open task. Preserve the
existing `budgetPeriod` query parameter and back/forward handling. Do not persist financial drafts
in a new localStorage store, remount `BudgetProvider`, or drop its pending command on navigation.

When limits are off, the current snapshot may not supply the concept's full category-observation
breakdown. Show the truthful single-pool presentation and existing inspection route until an
authoritative adapter exists; do not calculate category totals from a paginated source feed.
BUI-01 must record that presentation adaptation and any other field gap explicitly.

### Task extraction and command preservation

`BudgetItems.tsx` currently contains non-exported item/match/move/limit forms. `BudgetLifecycle`
composes frequency, accounts, rollover and controls. Extract controllers/forms incrementally;
do not mount the whole lifecycle component inside several panels or duplicate hidden forms.
Use a local typed task union with stable IDs, for example `goal(lineId?)`, `match(lineId)`,
`accounts`, `frequency`, `rollover`, `lifecycle`, `calculation`, `guide` and `data`.
Preserve existing request construction at first. Tests must compare resulting intents/receipts,
not just whether a replacement button can be clicked.

Choose exactly one focus/portal implementation for each task. If a Radix Sheet owns the focus
trap, do not nest `useDialogFocus` or a native `showModal()` around it. Dirty-form close, Escape,
outside click, period change and browser navigation all need the same preservation policy.
An in-flight/unknown write must retain the original request and route to `recover()`; closing a
panel never implies rollback. Prefer one panel with an internal review step over stacked dialogs.
